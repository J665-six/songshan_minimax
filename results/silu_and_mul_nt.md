# SiLU-and-Mul 优化尝试：五轮实验与最终结论

## 最终结论

**未跑赢基线。** 九齿生成的元素级 kernel 在这张卡上封顶在 ~457 GB/s，
而 torch 同类算子能到 1331 GB/s。差距不在算法，在代码生成。

## 五轮实验（seq=8192, bf16, D=14336）

| 版本 | 做法 | 耗时 | 带宽 |
|---|---|---|---|
| v1 | 二维 tile + 跨步输入 | 2.882 ms | 245 GB/s |
| v2 | 一维平铺 + 连续输入 | 1.540 ms | 457 GB/s |
| v3 | 二维 tile（BLOCK_M=1） | 2.694 ms | 262 GB/s |
| v4 | 固定行宽（2048）+ 动态 shape | 2.658 ms | 265 GB/s |
| v4-static | 固定行宽 + 静态 shape | 1.540 ms | 457 GB/s |
| **基线 IC** | — | **1.513 ms** | **465 GB/s** |
| torch mul | 参考上限 | 0.529 ms | 1331 GB/s |
| torch silu | 参考上限 | 0.710 ms | 662 GB/s |

## 排除的假设

| 假设 | 实验 | 结果 |
|---|---|---|
| 计算瓶颈（exp/sigmoid 贵） | 纯乘法 vs sigmoid | 1.5405 vs 1.5401 ms，**完全相同** |
| 跨步访问 | v2 改连续输入 | 245 → 457，只补回一半 |
| 访存上限 | torch 同形状三流运算 | 1331 GB/s，**硬件完全够** |
| program 数量太多 | 行宽 2048→14336（57344→8192 个 program） | 全部 1.54 ms，**无关** |
| 固定启动开销 | 规模 128→2048→8192 | 0.044→0.390→1.540 ms，**线性缩放，不是开销** |
| mask 未消除 | 静态 shape + 静态 tile | 仍 457 GB/s |

## 与成功案例的对比

| 算子 | 每元素内存操作 | 带宽 |
|---|---|---|
| RMSNorm | 1 读 1 写 + 行归约 | 851–899 GB/s |
| Add-RMSNorm | 2 读 2 写 + 行归约 | 1107–1184 GB/s |
| SiLU-and-Mul | 2 读 1 写，无归约 | **457 GB/s** |

规律：**带行归约的算子快，纯元素级的算子慢。**
推断是归约让编译器把整行物化到寄存器、按行向量化；而纯元素级路径走了
逐元素索引/掩码路径，向量化被破坏。

## 已做的上游修补

九齿 emitter 缺 `sigmoid` 映射（`ntl.sigmoid` 会生成裸 `sigmoid(...)`，
Triton 侧无此符号）。已在
`ninetoothed/backends/emitters/triton.py` 补 `"sigmoid": "tl.sigmoid"`。

## 如果要彻底解决

1. 在九齿后端把纯元素级路径的 mask 在"尺寸整除 tile"时静态化为 `None`
2. 或对元素级算子引入行内循环，复用归约路径的向量化
3. 或把 SiLU 融进 up-projection 的 GEMM epilogue，根本绕开这个 kernel

前两条属于"改进九齿编译器"，赛题允许且是加分项，但不是一两天能稳的活。
