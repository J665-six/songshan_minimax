> 本文档分三部分：
> 1. 把 H3 前向过程拆成算子序列（逐段，可对照源码）
> 2. 对照 InfiniCore 现有能力，标出**缺失算子**
> 3. 给出**优化选型**及实测结果

## 第一部分：H3 前向的算子分解

### 1.1 总览：一次 FL2VA 的六个阶段

```
① 文本编码      Qwen3-VL 32B
② 首帧编码      视频 VAE Encoder（Causal Conv3d）
③ 打包           patchify + index_copy 拼成单序列
④ 去噪 ×50      DiT 50 层
⑤ 视频解码      视频 VAE Decoder（36 层 ViT）
⑥ 音频解码      音频 VAE Decoder（DAC）
```

下面逐段给出算子序列。

---

### 1.2 阶段①：文本条件编码

源码：`transformers.Qwen3VLForConditionalGeneration`，H3 只取前 50 层。

```
input_ids ──► Embedding(151936, 5120)
                    │
                    ▼
            ┌───────────────────────────────┐
            │  × 50 层 Qwen3-VL Block        │
            │                                │
            │  RMSNorm → Linear(q,k,v)       │
            │  → RoPE(q,k)                   │
            │  → Attention                   │
            │  → Linear(o) → 残差            │
            │                                │
            │  RMSNorm → gate/up Linear      │
            │  → SiLU × up（SwiGLU）         │
            │  → down Linear → 残差          │
            └───────────────────────────────┘
                    │
                    ▼
            hidden_states [1, L, 5120]
```

**为什么只取前 50 层**：H3 需要的是中间层语义特征，而不是生成能力。
`MiniMaxH3ConditionEncoder` 里硬编码了 `num_hidden_layers = 50`，
并跳过 final norm 和 lm_head。

**算子清单**：

| # | 算子 | 形状 | 说明 |
|---|---|---|---|
| 1 | `Embedding` | [L] → [L, 5120] | 词嵌入 |
| 2 | `RMSNorm` | [L, 5120] | 每层 2 次 |
| 3 | `Linear` | [L,5120]×[5120,5120] | q/k/v/o，每层 4 次 |
| 4 | `RoPE` | [L,40,128] | q、k 各一次 |
| 5 | `Attention` | [L,40,128] | 40 头（Qwen3-VL 配置） |
| 6 | `Linear` | [L,5120]×[5120,25600] | gate+up 融合 |
| 7 | `SiLU` + `Mul` | [L,12800] | SwiGLU |
| 8 | `Linear` | [L,12800]×[12800,5120] | down |
| 9 | `Add` | [L,5120] | 残差，每层 2 次 |

### 1.3 阶段②：首帧编码（视频 VAE Encoder）

源码：`AutoencoderKLMiniMaxH3.encoder`，6 级 block。

```
首帧 [1,3,1,720,1280]
   │
   ├─► Causal Conv3d(3→128, k=3) ──► GroupNorm(32) ──► SiLU
   │        │
   │        └─► ResNet×2: [GroupNorm → SiLU → Conv3d → GroupNorm → SiLU → Conv3d] + 残差
   │
   ├─► Downsample(spatial×2, temporal×1)
   ├─► Block(256) + Downsample(×2, ×2)
   ├─► Block(256) + Downsample(×2, ×2)
   ├─► Block(512) + Downsample(×2, ×1)
   ├─► Block(512) + Downsample(×1, ×1)
   ├─► Block(1024)
   │
   ▼
GroupNorm ──► SiLU ──► Conv3d(1024→48) ──► chunk(2) ──► mean/logvar
   │
   ▼
首帧 latent [1,24,1,45,80]
```

**算子清单**：

| # | 算子 | 出现次数 | 说明 |
|---|---|---|---|
| 1 | `CausalConv3d` | 6 + 12×2 = 30 | 时间维因果 padding |
| 2 | `GroupNorm`（32 组，eps=1e-6） | ~50 | **InfiniCore 缺失** |
| 3 | `SiLU` | ~25 | 存在 |
| 4 | `Add` | 12 | 残差 |
| 5 | `ReflectPad`（3D） | 每次 conv 前 | 需确认支持 |
| 6 | `Chunk` / `Slice` | 1 | 分均值方差 |

### 1.4 阶段③：打包（patchify + 拼接）

源码：`MiniMaxH3Transformer3DModel.forward` 第 1 步。

```python
# 1) 各模态投影
video_embeds = proj_in(hidden_states)      # [Nv, 24*1*2*2] → [Nv, 5376]，fp32
audio_embeds = audio_proj_in(audio_hidden) # [Na, 32]      → [Na, 5376]，fp32
text_embeds  = context_embedder(encoder_hidden_states)  # [Nt,5120] → [Nt,5376]，bf16
text_embeds  = token_refiner(text_embeds)  # 2 层标准 block

# 2) 按索引散射进统一序列（先文本、再视频、再音频）
hidden_states = zeros([1, seq_len, 5376])
hidden_states = index_copy(1, text_indices,  text_embeds)
hidden_states = index_copy(1, video_indices, video_embeds.to(bf16))
hidden_states = index_copy(1, audio_indices, audio_embeds.to(bf16))
```

**这个设计的意义**：文本、视频、音频在**同一条序列**里做 self-attention，
所以不存在 cross-attention。文本 token 通过 attention 直接影响音视频 token。

**算子清单**：

| # | 算子 | 说明 |
|---|---|---|
| 1 | `Linear`（proj_in / audio_proj_in / context_embedder） | 三个模态投影，fp32/bf16 混合 |
| 2 | `TokenRefiner`（2 层） | RMSNorm + Attention + FFN，无 AdaLN |
| 3 | `index_copy` | 3 次，散射进打包序列 |
| 4 | `zeros` | 序列缓冲初始化 |
| 5 | `cast` | video/audio 从 fp32 转 bf16 |

### 1.5 阶段④：DiT 去噪（50 层）

#### 4.1 去噪前的准备（每步一次）

```
timestep [0,1]
   │
   ├─► time_proj：sinusoidal 编码 ──► [1, 256]        ← fp32
   │
   ├─► time_embedder：Linear(256→5376) + SiLU + Linear(5376→2688)   ← fp32
   │
   ▼
temb [1, 2688]

adaln_indices = timestep_indices × 3 + token_tags   # 每行查表下标
   │
   ▼
每个 block 的 adaln_proj：
   temb → SiLU → Linear(2688 → 6×5376) → chunk(6)
   → shift_msa, scale_msa, gate_msa, shift_mlp, scale_mlp, gate_mlp
```

**关键观察**：`adaln_proj` 的输出**只依赖 (timestep, modality)**，
与序列长度无关。因为一条序列里只有少数几个不同的 `(t, modality)` 组合
（典型 3 个：视频、音频、文本条件），所以每步只需算 3 次而不是 11 万次。

这就是 `MiniMaxH3ConditionEncoder` 里"AdaLN 表预计算"优化的依据。
源码注释也提到：约 **39% 的 DiT 参数（13B / 33B）在 AdaLN 分支上**。

#### 4.2 单个 Block 的算子序列

```
输入 x [seq_len, 5376]
│
├─① RMSNorm(norm1)                     [seq,5376] → [seq,5376]
├─② Mul + Add：x × (1+scale) + shift     AdaLN 调制
├─③ Linear(to_q/k/v)                   [seq,5376] → [seq,5376] ×3
├─④ reshape → [seq, 56, 128]
├─⑤ RMSNorm(norm_q/norm_k)             在 head_dim=128 上归一化
├─⑥ RoPE(q, k)                         3 轴（t,h,w）
├─⑦ Attention（56 头，全序列 self-attn）
│     需要 T×T 的注意力矩阵，T = seq_len
├─⑧ reshape → [seq, 5376] ─► Linear(to_out)
├─⑨ × gate_msa ─► + 残差
│
├─⑩ RMSNorm(norm2)
├─⑪ Mul + Add：AdaLN 调制
├─⑫ Linear(gate+up)：[seq,5376] → [seq,28672]   （fusion: gate 与 up 合并）
├─⑬ SiLU(gate) × up                   → [seq,14336]
├─⑭ Linear(down)：[seq,14336] → [seq,5376]
├─⑮ × gate_mlp ─► + 残差
▼
输出 [seq_len, 5376]
```

**每层算子频次**：

| 算子 | 每层次数 | 50 层合计 |
|---|---|---|
| `RMSNorm` | 4（norm1, norm2, norm_q, norm_k） | **200** |
| `Linear` | 6（q,k,v,out,gate/up,down） | 300 |
| `RoPE` | 2（q,k） | 100 |
| `Attention` | 1 | 50 |
| `SiLU` | 1（FFN）+ AdaLN 内 1 | ~100 |
| `Mul` | 4（2 AdaLN + gate 残差 + swiglu） | 200 |
| `Add` | 2（两处残差） | 100 |

#### 4.3 每步之后的采样

```
模型输出 video_velocity, audio_velocity
   │
   ▼
scheduler.step：
   x = x + dt × velocity        （一阶 Euler，取决于 scheduler 具体实现）
```

这部分是**极小的逐元素运算**，不是瓶颈。

### 1.6 阶段⑤：视频 VAE 解码（36 层 ViT）

源码：`MiniMaxH3VideoViTDecoder3d`。

```
latent [1,24,31,45,80]
   │
   ├─► 分块（tile 256×256，重叠 64）
   ├─► 每块内：patch 化为 token 序列
   │
   ▼
proj_in: Linear(24 → 2048)              ← fp32
   │
   ├─► 追加 4 个 register token + 1 个 zero token
   │
   ├─► 3 轴 RoPE（t/h/w，theta=100，ratio=0.75）
   │
   ▼
┌──────────────────────────────────────┐
│  × 36 层 MiniMaxH3VideoTransformerBlock│
│                                       │
│  RMSNorm(norm1, affine) → Attention   │
│    ├─ Linear(to_q/k/v) 2048→2048      │
│    ├─ RMSNorm(norm_q/k) 逐头 64 维     │
│    ├─ 3 轴 RoPE                        │
│    ├─ Attention（32 头 × 64）          │
│    └─ Linear(to_out)                  │
│  × scale1 + 残差                       │
│                                       │
│  RMSNorm(norm2, affine) → SwiGLU FFN  │
│    ├─ Linear(2048 → 10922) gate+up    │
│    ├─ SiLU(gate) × up                 │
│    ├─ Linear(10922 → 2048)            │
│    └─ × scale2 + 残差                 │
└──────────────────────────────────────┘
   │
   ├─► LayerNorm(norm_out)              ← fp32
   ├─► proj_out: Linear(2048 → 3072)    ← 3ch × 4 × 16 × 16
   ├─► reshape → [1,3,31×4,45×16,80×16]
   │
   ▼
像素 [1,3,124,720,1280]
```

**注意**：这里的 FFN 中间维是 `2048 × 4 × 2/3 ≈ 5461`，而非 10922 的一半；
具体由 SwiGLU 的 `inner_dim` 计算决定，需以实际 config 为准。

**每层算子频次（36 层）**：

| 算子 | 每层 | 36 层合计 |
|---|---|---|
| `RMSNorm` | 4 | 144 |
| `Linear` | 5 | 180 |
| `RoPE` | 2 | 72 |
| `Attention` | 1 | 36 |
| `SiLU` | 1 | 36 |
| `LayerNorm` | 1（仅最后一层） | 1 |

### 1.7 阶段⑥：音频 VAE 解码

源码：`MiniMaxH3AudioBigVGANDecoder`。

```
音频 latent [B, 32, T]
   │
   ├─► Conv1d(32 → 1024)
   │
   ▼
┌──────────────────────────────────────┐
│  上采样链（7 级，rates = [5,5,2,2,2,2,2]）│
│                                       │
│  每级：                                │
│    LeakyReLU(0.1)                     │
│    ConvTranspose1d(c_in → c_out, k, s)│
│    ┌─────────────────────────────┐    │
│    │ 3 × ResidualBlock            │    │
│    │   LeakyReLU → Conv1d(dilated) │    │
│    │   → Snake 激活 → Conv1d(dilated)│   │
│    │   + 残差                      │    │
│    └─────────────────────────────┘    │
│                                       │
│  （第 4 级后接 Causal Attention + GEGLU）│
└──────────────────────────────────────┘
   │
   ├─► LeakyReLU → Conv1d(→ 1)
   ▼
波形 [B, 1, 32kHz × 5.17s]
```

**算子清单**：

| # | 算子 | 频率 | InfiniCore 状态 |
|---|---|---|---|
| 1 | `Conv1d`（含 dilation） | 高 | ⚠️ 仅 `conv.h` 通用接口，未见 1D 专用 |
| 2 | `ConvTranspose1d` | 7 | ❌ **缺失** |
| 3 | `Snake`（`x + sin²(αx)/β`） | 21 | ❌ **缺失** |
| 4 | `LeakyReLU` | ~28 | ⚠️ 需确认 |
| 5 | `Causal Attention` | 1 | ✅（`attention.h`） |
| 6 | `GEGLU` | 1 | ⚠️ 需用 `Linear + GELU + Mul` 组合 |

### 2.2 缺口汇总（按影响排序）

| 优先级 | 缺失算子 | 影响的阶段 | 调用频次 | 开发难度 |
|---|---|---|---|---|
| **P0** | `group_norm` | 视频 VAE 编码器 | ~50 | 中（归约 + 仿射） |
| **P0** | `conv_transpose1d` | 音频 VAE 解码 | 7 | 中 |
| P1 | `snake` | 音频 VAE 解码 | 21 | 低（逐元素） |
| P1 | `cat` | 多模态拼接 | 少 | 低 |
| P2 | `cast`（infiniop 层） | 混合精度 | 多 | 低 |
| P2 | `leaky_relu` | 音频 VAE | ~28 | 低 |

**结论**：要完整迁移 H3，**必须先补 `group_norm`**（视频 VAE 的门槛），
其次是 `conv_transpose1d` 和 `snake`（音频 VAE 的门槛）。

## 第三部分：优化选型与实测结果

### 3.1 选型依据

不是所有算子都值得优化。评估维度：

| 维度 | 说明 |
|---|---|
| **调用频次** | 每前向调用多少次 |
| **访存特征** | 是访存瓶颈还是计算瓶颈 |
| **基线效率** | 离峰值带宽还有多远 |
| **实现难度** | 九齿能否表达 |

按这四个维度扫描 H3 的算子：

| 算子 | 频次/前向 | 瓶颈类型 | 基线带宽 | 结论 |
|---|---|---|---|---|
| **RMSNorm** | **200（DiT）+ 144（VAE）** | 访存 | 419 GB/s（31%） | ⭐ **优选** |
| **Add-RMSNorm** | 100 | 访存 | 605 GB/s（45%） | ⭐ **优选** |
| `Attention` | 50 + 36 | 计算 | — | 复杂，风险高 |
| `Linear` | 300 + 180 | 计算 | 325 TFLOPS（接近峰值） | 无空间 |
| `SiLU-and-Mul` | 50 + 36 | 访存 | 465 GB/s | 尝试过，失败（见下） |
| `RoPE` / `mRoPE` | 100 + 72 | 访存+计算 | 未测 | 中等潜力 |
| `timestep_embedding` | 50 | 极小 | — | 无价值 |

### 3.2 已完成的优化

#### （1）RMSNorm

**优化前**（InfiniCore 基线）：

```
seq=8192,  bf16  →  0.419 ms  →  419 GB/s  →  峰值的 31%
seq=16384, bf16  →  0.833 ms  →  421 GB/s
```

**优化后**（九齿实现）：

```
seq=8192,  bf16  →  0.207 ms  →  851 GB/s  →  2.02×
seq=16384, bf16  →  0.392 ms  →  899 GB/s  →  2.13×
seq=8192,  fp16  →  0.152 ms  → 1157 GB/s  →  2.40×
seq=16384, fp16  →  0.291 ms  → 1213 GB/s  →  2.48×
```

**改了什么**：把"两次访存"改成"一次访存"——整行读入后直接算均方、
归一化、写出，中间不落盘。

**没改什么**：公式、eps、权重应用顺序、累加精度（仍为 fp32）。

#### （2）Add-RMSNorm

**优化前**：

```
seq=8192,  bf16  →  0.570 ms  →  605 GB/s
seq=16384, bf16  →  1.154 ms
```

**优化后**：

```
seq=8192,  bf16  →  0.318 ms  → 1107 GB/s  →  1.79×
seq=16384, bf16  →  0.627 ms  → 1124 GB/s  →  1.84×
seq=8192,  fp16  →  0.301 ms  → 1171 GB/s  →  1.55×
```

**改了什么**：把"先算 residual 再归一化"的两个 kernel 合并成一个，
一次读入 a、b，一次写出 y 和 res。

### 3.3 失败案例：SiLU-and-Mul

尝试了 5 种实现，**全部没有超过基线**：

| 版本 | 做法 | 结果 |
|---|---|---|
| v1 | 二维 tile + 跨步输入 | 245 GB/s（0.53×） |
| v2 | 一维平铺 + 连续输入 | 457 GB/s（0.98×） |
| v3 | 二维 tile | 262 GB/s |
| v4 | 固定行宽 | 265 GB/s |
| v4-static | 静态 shape | 457 GB/s |

**根因**：九齿对"纯元素级"算子的代码生成会退化为逐元素掩码访问，
而"带行归约"的算子能保持向量化。torch 在同样形状下能跑到 1331 GB/s，
说明是**工具链限制，不是硬件限制**。

后续的效率探针（见第四部分 4.1）进一步确认：这个退化与输入个数无关，
1~4 输入的纯元素级 kernel 全部稳定在峰值的 22–23%。

## 第四部分：优化路线图（基于实测效率分区）

### 4.1 决定性发现：九齿的效率有明确分区

在补齐 AdaLN 与效率探针两组实验后，得到一条清晰规律：

| 输入数 | 九齿带宽 | 占峰值 | torch 带宽 | 占峰值 |
|---|---|---|---|---|
| 1（纯拷贝） | 304 GB/s | **23%** | 1307 GB/s | 97% |
| 2 | 313 GB/s | 23% | 1310 GB/s | 97% |
| 3 | 306 GB/s | 23% | 880 GB/s | 65% |
| 4 | 302 GB/s | 22% | 732 GB/s | 54% |

**九齿在纯元素级场景下，无论几个输入，都稳定在峰值的 22–23%。**

而带行归约的算子实测：

| 算子 | 九齿带宽 | 占峰值 |
|---|---|---|
| RMSNorm | 852–1213 GB/s | 64–90% |
| Add-RMSNorm | 962–1184 GB/s | 72–88% |

**结论：九齿的优势区只有"带归约"一类；纯元素级一律不能走九齿。**

原因推断：归约强制编译器把整行载入寄存器、按行向量化，绕开了元素级路径的
逐元素索引/掩码生成。一旦去掉归约，就退化为低效访问。

### 4.2 因此修正一条原有判断

原计划认为"AdaLN 三连融合成一个 affine 能提速"。实测结果相反：

| 方案 | 访存趟数 | 实测耗时 | 相对 |
|---|---|---|---|
| torch 三次 kernel（`mul → add → add`） | 9 | 0.6012 ms | 1.00× |
| 九齿融合一次 kernel | 4 | 1.2139 ms | **0.495×** |

**注意**：AdaLN 的 scale/shift/gate 一次推理 **5000 次调用**（2 次/层 × 50 层 × 50 步），
把它换成 `addcmul` 的收益是确定的。

访存理论上少了一半，但因为九齿元素级效率只有 22%，**融合反而慢 2 倍**。
数值上两者完全等价（`cos = 1.00000012`，`max_abs = 0`）。

**这条要写进报告的失败案例**：融合的推理链是对的（减少访存），
但当前工具链做不到，因此必须改用非九齿路径。

### 4.3 修正后的优化清单

#### P0 —— 已完成，但尚未进入正式路径

| # | 算子 | 实测收益 | 阻塞 |
|---|---|---|---|
| 1 | RMSNorm | 2.02×（bf16）/ 2.36×（fp16） | 九齿 AOT 导出不可用 |
| 2 | Add-RMSNorm | 1.80×（bf16）/ 1.52×（fp16） | 同上；且需跨 block 重排 |

#### P1 —— 不依赖九齿，当前唯一能落地的优化

| # | 目标 | 做法 | 依赖 |
|---|---|---|---|
| 3 | **AdaLN 三连** | `mul+add+add` → `addcmul` + `add` | InfiniCore 内置 `addcmul` |
| 4 | **门控残差** | `mul + add` → `addcmul` | 同上 |
| 5 | **打包路径** | `zeros + 3×index_copy` → 单次 pack kernel | 需新写 |

`addcmul`（`out = input + tensor1 × tensor2 × value`）在 InfiniCore 中已存在
（`include/infiniop/ops/addcmul.h` + `python/infinicore/ops/addcmul.py`），
不是九齿生成，属于框架现有能力。

#### P2 —— 需先探明可行性

| # | 目标 | 障碍 |
|---|---|---|
| 6 | `mRoPE` | 有 DCU 实现，未测性能 |
| 7 | `conv` 3D | 签名支持 N 维，**但未实跑验证** |
| 8 | `silu_and_mul` | 九齿元素级 22%，应改用现有 `swiglu` |

#### P3 —— 明确不做

| 算子 | 理由 |
|---|---|
| `linear` / `matmul` | 325 TFLOPS，已接近峰值 |
| `attention` | C++ 集成依赖 AOT，海光不可用 |
| 任何元素级九齿 kernel | 22% 峰值，融合反而更慢 |

### 4.4 为什么 RMSNorm 类算子收益最大

1. **调用频次最高**：DiT 50 层 × 4 次 + VAE 36 层 × 4 次 = **344 次/前向**（不含去噪步数）
2. **纯访存**：没有计算依赖，性能上限清晰（就是带宽）
3. **基线效率低**：只有峰值的 32%–57%，有 2 倍以上空间
4. **九齿擅长**：行归约形态能生成高质量代码（实测 82%–90% 峰值）

## 第五部分：我的判断与思路

以下是基于全部实测数据形成的判断，不是推测。

### 5.1 当前最大的问题不是"缺算子"，而是"优化没上线"

从数据看，DiT 主干的算子链是完整的，VAE 两端缺 4–5 个算子——这确实是工程量，
但它属于"能不能跑通"，不属于"跑得快不快"。

真正的问题是：**两个已经实测 2× 的 kernel，端到端收益目前是 0。**

原因是它们以独立脚本形式存在，而 C++ 推理路径仍调用原始实现。
这直接影响工程质量 20 分（我自己的验收标准 A2 条款就写了"正式路径不走 torch 回退"）。

### 5.2 AOT 是唯一真正的技术阻塞

九齿有两条代码生成路径：

| 路径 | 状态 | 用途 |
|---|---|---|
| JIT（`ninetoothed.make`） | ✅ 实测可用 | Python 侧调用 |
| AOT（`caller="cuda"`） | ❌ `triton.tools.compile` 非零退出 | 导出 C++ 可调用代码 |

比赛要求"经九齿编译链生成目标代码"并进入正式路径，**必须走 AOT**。
这条不通，所有九齿优化都停留在"能测不能上"。

所以我认为：**接下来投入产出比最高的动作是攻克 AOT**，而不是再造新 kernel。
造出第 3 个、第 4 个 2× 的 kernel，端到端依然是 0。

### 5.3 元素级优化必须绕开九齿

实测证明九齿元素级只有 22% 峰值，任何"用九齿融合元素级算子"的想法都会失败。
但这不等于元素级没有优化空间——**torch 能做到 65%**，`addcmul` 这类
InfiniCore 内置融合算子也是现成的。

所以元素级优化的正确做法是：

```
优先用 InfiniCore 已有的融合算子（addcmul / swiglu / add_rms_norm）
  ↓ 没有的话
退回 torch 的多算子串联（65% 峰值，比九齿的 22% 好）
  ↓ 仍然不够
才考虑九齿（且只在带归约的场景）
```

### 5.4 评分视角下的取舍

| 评分项 | 权重 | 我的判断 |
|---|---|---|
| 视频规格 20% | 最容易拿 | 用 torch VAE 解码锁死，不迁 InfiniCore |
| 视频相似度 30% | 不能冒险 | 只换数值等价的算子（RMSNorm 系，cos≈1.0） |
| 性能 30% | 主战场 | 在 DiT；但受限于 AOT，短期内只能靠 addcmul 类改动 |
| 工程质量 20% | 可控 | 把 kernel 放进 `ops/<op>/ninetoothed/` 并登记分发 |

我的判断是：**在 AOT 解决前，性能分天花板很低**；
但如果把"为什么没上线"讲清楚（工具链限制 + 数据支撑），
工程质量分反而能拿住——评审看的是分析深度，不是单纯的数字。

### 5.5 如果只有 3 天

| 天 | 动作 |
|---|---|
| Day 1 | 攻 AOT；同时把 AdaLN 改 `addcmul`（不依赖 AOT，可立即落地） |
| Day 2 | 若 AOT 通，接入 RMSNorm；若不通，转做 group_norm 补齐 VAE 缺口 |
| Day 3 | 出数据、补文档、录截图 |

核心策略：**AOT 是高风险高回报，addcmul 是低风险保底，两条腿走。**
