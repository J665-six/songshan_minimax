# 算子运行验证与消融实验

> 本目录回答一个问题：**加速比是不是真的来自算子替换？**
>
> 方法是消融（ablation）：固定一切变量，只切换算子实现。

---

## 一、实验设计

### 1.1 控制变量

要让"加速比"可信，必须保证除算子实现外**其他全部相同**：

| 变量 | 控制方式 |
|---|---|
| 硬件 | 同一个 Slurm 作业、同一张 DCU（`--gres=dcu:1`） |
| 输入数据 | 固定随机种子 `SEED=20261030`，同一份张量 |
| 张量形状 | `[8192, 5376]`，与 H3 的 hidden_size 一致 |
| 数据类型 | bf16 / fp16 分别测 |
| 计时方法 | 同一个 `bench()`：10 次预热 + 50 次迭代 + 前后 `synchronize()` |
| 计轮次 | 每组连测 3 轮，取中位数 |
| 数值参考 | 同一个 PyTorch fp32 实现 |
| **唯一变量** | **算子实现：InfiniCore 基线 vs NineToothed** |

### 1.2 为什么两个实现共享同一块显存

`from_torch()` 内部是 `from_blob(torch_tensor.data_ptr())`——**零拷贝**。
所以基线和九齿拿到的是**物理上同一份输入数据**，不存在"数据不一致"的可能。

```python
x = torch.randn(seq, HIDDEN, ...)      # 唯一一份输入
icx = from_torch(x)                     # 基线视图
kernel(x, w, out_nt)                    # 九齿直接用 torch 张量
```

### 1.3 参考实现

```python
def torch_rms_ref(x, w):
    xf = x.float()                              # fp32 累加
    ms = xf.pow(2).mean(dim=-1, keepdim=True)
    return (xf / torch.sqrt(ms + EPS) * w.float()).to(x.dtype)
```

两个实现都与这份参考对比，误差指标一致。

## 三、实验结果

### 3.1 实验一：RMSNorm

| dtype | 基线 | 九齿 | 加速比 | 基线带宽 | 九齿带宽 |
|---|---|---|---|---|---|
| bf16 | 0.4171 ms | **0.2066 ms** | **2.02×** | 422 GB/s（32%） | **852 GB/s（64%）** |
| fp16 | 0.3612 ms | **0.1530 ms** | **2.36×** | 488 GB/s（36%） | **1152 GB/s（86%）** |

### 3.2 实验二：Add-RMSNorm

| dtype | 基线 | 九齿 | 加速比 | 基线带宽 | 九齿带宽 |
|---|---|---|---|---|---|
| bf16 | 0.5694 ms | **0.3167 ms** | **1.80×** | 619 GB/s（46%） | **1113 GB/s（83%）** |
| fp16 | 0.4634 ms | **0.3040 ms** | **1.52×** | 760 GB/s（57%） | **1159 GB/s（87%）** |

### 3.3 正确性

| 实验 | dtype | 基线 cos | 九齿 cos | 基线 max_abs | 九齿 max_abs |
|---|---|---|---|---|---|
| RMSNorm | bf16 | 1.00000012 | 0.99999994 | 3.13e-2 | 6.25e-2 |
| RMSNorm | fp16 | 1.00000000 | 0.99999994 | 7.81e-3 | 7.81e-3 |
| Add-RMSNorm | bf16 | 0.99999619 | 0.99999613 | 6.25e-2 | 6.25e-2 |
| Add-RMSNorm | fp16 | 0.99999988 | 0.99999994 | 7.81e-3 | 7.81e-3 |

**两个实现的误差处于同一量级**，九齿没有引入额外精度损失。
`6.25e-2` 是 bf16 在该量级上的 1 个 ULP（2⁻⁴），是表示精度下限。

### 3.4 稳定性

每个实现连测 3 轮，波动情况：

| 实验 | 3 轮耗时 | 波动 |
|---|---|---|
| RMSNorm bf16 基线 | 0.4171 / 0.4169 / 0.4180 | 0.26% |
| RMSNorm bf16 九齿 | 0.2066 / 0.2066 / 0.2068 | 0.10% |
| Add-RMSNorm bf16 基线 | 0.5687 / 0.5696 / 0.5694 | 0.16% |
| Add-RMSNorm bf16 九齿 | 0.3168 / 0.3167 / 0.3166 | 0.06% |

最大波动 0.26%，远低于 5% 的判定阈值，说明测量可信。

## 四、消融逻辑：为什么能证明加速来自算子

如果加速来自其他因素，会出现以下情况，但都**没有出现**：

| 可能的干扰 | 是否发生 | 证据 |
|---|---|---|
| 输入数据不同 | ❌ | 同一份 torch 张量，零拷贝共享 |
| 硬件不同 | ❌ | 同一个作业、同一张卡 |
| 计时方式不同 | ❌ | 同一个 `bench()` 函数 |
| 编译缓存导致假快 | ❌ | 两个实现都跑 10 次预热后才计时 |
| 降精度换速度 | ❌ | 两者都用 bf16/fp16，误差同量级 |
| 减少计算量 | ❌ | 公式完全一致，输出对标 fp32 参考 |

**唯一变化的量就是算子实现**，因此耗时差异只能归因于此。

### 反向验证：峰值带宽对照

如果九齿真的更快，它的带宽应该更接近硬件峰值。实测：

```
硬件峰值（device-to-device copy）  1336 GB/s
基线 RMSNorm                       422 GB/s  → 32%
九齿 RMSNorm                       852 GB/s  → 64%
九齿 Add-RMSNorm                  1113 GB/s  → 83%
```

**九齿把访存效率从 1/3 推到 2/3 以上**，这符合"减少一次访存往返"的预期，
也与代码改动方向一致——不是靠取巧，是靠真减少了内存流量。

## 五、如何复现

### 5.1 一键复现

```bash
# 本地：同步代码到集群
powershell -File scripts/sync.ps1

# 集群：提交作业跑消融
srun --partition=hx1hdnormal --ntasks=1 --cpus-per-task=8 \
     --gres=dcu:1 --time=00:20:00 bash -lc '
  source ~/setup_env.sh
  cd ~/work/infinilm
  python tasks/ablation_run.py --seqs 8192 --dtypes bf16,fp16 \
    2>&1 | tee results/ablation_console.log
'
```

## 六、已知局限

1. **只测了算子级，未测端到端**
   单卡装不下 33B DiT（62 GB > 64 GB 且需激活），无法跑完整 FL2VA。
   端到端收益需 8 卡阶段验证。

2. **序列长度只测 8192**
   真实推理的 token 数约 11 万（720p/124 帧）。
   但趋势已验证：seq 从 8192 到 16384，加速比从 2.02× 升到 2.13×，
   说明规模越大优势越明显。

3. **未接入 C++ 正式推理路径**
   九齿的 AOT 导出在平台的 Triton 上不可用（`triton.tools.compile` 非零退出）。
   当前是"独立可运行、可测量"形态。
