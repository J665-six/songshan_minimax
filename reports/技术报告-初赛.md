# 基于 InfiniLM 与 InfiniCore 的 MiniMax-H3 首帧视频生成适配与优化

## 技术报告（初赛）

---

## 一、摘要

本报告汇报我们在国产海光 DCU（BW / gfx936）单卡环境下，使用 NineToothed（九齿）
对 MiniMax-H3 推理链路中两个高频算子进行重写的阶段性结果：

| 算子 | 相对 InfiniCore 基线加速比 | 达成带宽 | 峰值带宽占比 |
|---|---|---|---|
| RMSNorm | **2.02× – 2.48×** | 851 – 1213 GB/s | 63% – 90% |
| Add-RMSNorm（融合） | **1.55× – 1.84×** | 962 – 1184 GB/s | 72% – 88% |

两个算子的输出与 PyTorch fp32 参考实现余弦相似度均 ≥ 0.99999，
三轮重复测量波动 < 0.4%。

同时，我们对第三个算子 SiLU-and-Mul 做了五轮优化尝试，全部未能超过基线
（最好成绩 0.98×），并定位到根因在于九齿当前代码生成对"纯元素级"路径的
向量化处理，已记录为失败案例与已知限制。

## 五、被优化的算子

### 5.1 为什么选这两个

MiniMax-H3 的 DiT 主干共 50 层，视频 VAE 解码器是 36 层 ViT，
两层结构里都反复出现同一组归一化模式：

- 每个 block 有 **2 个 RMSNorm**（注意力前、FFN 前）
- 残差分支上是 **Add + RMSNorm** 的融合模式

按单次前向估算：

```
RMSNorm 调用次数 ≈ 50×2（DiT）+ 36×2（VAE）= 172 次
```

在单卡 33B 参数、50 步去噪的规模下，这类"每次只读写几百 MB 却要跑几百次"的算子，
其累计开销不可忽略。而它们都是**纯访存型**，理论上限清晰、优化收益确定，
适合作为单卡阶段的目标。

### 5.2 基线实现的水平

| 算子 | 基线耗时（seq=8192, bf16） | 有效带宽 | 峰值占比 |
|---|---|---|---|
| RMSNorm | 0.419 ms | 419 GB/s | 31% |
| Add-RMSNorm | 0.570 ms | 605 GB/s | 45% |

两者都明显低于峰值，说明存在优化空间。

## 六、优化思路

### 6.1 技术路线

采用九齿的 **arrange-and-apply** 范式，把"数据怎么切"与"每个切片算什么"
分开描述：

```python
def arrangement(x, w, y):
    y_a = y.tile((BLOCK_M, N))
    x_a = x.tile((BLOCK_M, N))
    w_a = w.tile((N,)).expand((x_a.shape[0], -1))
    return x_a, w_a, y_a

def application(x, w, y):
    mean_square = ntl.sum(x * x, axis=1) / x.shape[1]
    inv_rms = 1.0 / ntl.sqrt(mean_square + 1e-5)
    y = x * inv_rms[:, None] * w
```

### 6.2 几个关键取舍

**（1）tile 覆盖整行，而非部分列**

把归一化维度 N（H3 的 hidden_size = 5376）设为编译期常量，让一次 tile 就覆盖整行。
这样行归约不需要跨 tile 累积，省掉中间状态和二次遍历。

**（2）BLOCK_M = 1**

我们试验了 BLOCK_M ∈ {1, 2, 4}。当 BLOCK_M > 1 时结果错误：
余弦相似度恰好等于 1/√M（M=2 时 0.707，M=4 时 0.500），
说明只有 tile 的第一行被写入，其余行保持未初始化。

这是九齿在多行 tile 广播赋值上的限制，我们选择 BLOCK_M = 1 规避，
并以行方向的 program 数保证并行度（单步上万 token，program 数量充足）。

**（3）归约在 fp32 下进行**

`ntl.sum` 对 bf16 输入做归约时向上转型为 fp32，与 PyTorch 参考实现的数值路径一致。
输出仍写回 bf16，误差处于表示精度范围内（见第七节）。

**（4）eps 与常量内联**

九齿的 SSA 后端不识别模块级 Python 常量（会报 `Unknown value 'N'`），
因此 kernel 内使用字面量与 `x.shape[1]` 这样的编译期符号。

**（5）Add-RMSNorm 的融合**

把"残差相加"和"归一化"合并到一个 kernel：一次读入 a、b，一次写出归一化结果 y
和新的残差 res，避免中间张量的额外往返。

## 七、正确性验证

### 7.1 方法

以 PyTorch 的 fp32 计算为参考：

```python
xf = x.float()
ms = xf.pow(2).mean(dim=-1, keepdim=True)
ref = (xf / torch.sqrt(ms + eps) * w.float()).to(dtype)
```

对比指标：余弦相似度、最大绝对误差、最大相对误差。

### 7.2 RMSNorm

| dtype | seq | cos | max_abs | max_rel |
|---|---|---|---|---|
| bf16 | 1 | 1.000000 | 3.13e-2 | 7.41e-3 |
| bf16 | 127 | 1.000000 | 6.25e-2 | 7.75e-3 |
| bf16 | 8192 | 1.000000 | 6.25e-2 | 7.75e-3 |
| bf16 | 16384 | 1.000000 | 6.25e-2 | 7.81e-3 |
| fp16 | 1 | 1.000000 | 3.91e-3 | 9.76e-4 |
| fp16 | 16384 | 1.000000 | 7.81e-3 | 4.76e-2 |

### 7.3 Add-RMSNorm

| dtype | seq | cos(y) | cos(res) | max_abs | max_rel |
|---|---|---|---|---|---|
| bf16 | 2048 | 0.999996 | 1.000000 | 6.25e-2 | 7.81e-3 |
| bf16 | 8192 | 0.999996 | 1.000000 | 6.25e-2 | 7.97e-3 |
| bf16 | 16384 | 0.999996 | 1.000000 | 6.25e-2 | 8.03e-3 |
| fp16 | 8192 | 1.000000 | 1.000000 | 1.56e-2 | 5.88e-2 |
| fp16 | 16384 | 1.000000 | 1.000000 | 1.56e-2 | 3.23e-2 |

### 7.4 关于误差的说明

- bf16 的 `max_abs = 6.25e-2` 恰好等于该数值量级上的 **1 个 ULP**（2⁻⁴），
  属于 bf16 表示精度的下限，不是实现缺陷。
- fp16 的 `max_rel` 偏大（最高 5.88e-2）出现在**接近 0 的元素**上，
  此时分母极小导致相对误差放大；对应绝对误差仅 1.56e-2。
- 余弦相似度全部 ≥ 0.99999，说明整体方向与参考完全一致。

## 九、对九齿编译器的贡献

### 9.1 修复 sigmoid 映射缺失

`ninetoothed.language` 中的 `ntl.sigmoid` 经前端会生成裸 `sigmoid(...)` 调用，
而 Triton 侧并无该符号，导致编译报 `NameError('sigmoid is not defined')`。

根因是 `ninetoothed/backends/emitters/triton.py` 的内建函数映射表缺少 `sigmoid` 条目
（该表已有 `sin`/`sinh`/`sqrt` 等，唯独漏了 `sigmoid`）。

我们补充了：

```python
"sinh": "tl.sinh",
"sigmoid": "tl.sigmoid",   # 新增
```

同时发现另一个未修复的上游问题：`ntl.exp` 会生成 `tl.exp(_nt_exp_input(...))`，
但 `_nt_exp_input` 这个辅助函数在生成的模块里并不存在，属同类缺陷。

### 9.2 一份关于工具能力的实测判断

对比三个算子的结果，可以给出一个明确的工程结论：

| 算子 | 内存操作模式 | 达成带宽 |
|---|---|---|
| RMSNorm | 1 读 1 写 + 行归约 | 851 – 899 GB/s |
| Add-RMSNorm | 2 读 2 写 + 行归约 | 1107 – 1184 GB/s |
| SiLU-and-Mul | 2 读 1 写，**无归约** | **457 GB/s** |

**九齿当前版本对"带行归约"的算子能生成接近峰值的代码，
对"纯元素级流式"算子则明显退化。**
这一点在选型时非常关键：同样的写法，结果可能相差 2.5 倍。

## 十、失败案例与已知限制

### 10.1 SiLU-and-Mul：五轮尝试，未跑赢基线

| 版本 | 做法 | 耗时 | 带宽 |
|---|---|---|---|
| v1 | 二维 tile + 跨步输入 | 2.882 ms | 245 GB/s |
| v2 | 一维平铺 + 连续输入 | 1.540 ms | 457 GB/s |
| v3 | 二维 tile（BLOCK_M=1） | 2.694 ms | 262 GB/s |
| v4 | 固定行宽 2048 | 2.658 ms | 265 GB/s |
| v4-static | 固定行宽 + 静态 shape | 1.540 ms | 457 GB/s |
| 基线 | InfiniCore | 1.513 ms | 465 GB/s |
| 参考上限 | torch `mul` | 0.529 ms | 1331 GB/s |

正确性始终达标（cos = 1.000000），但性能没有突破。

**逐条排除的假设：**

| 假设 | 实验 | 结论 |
|---|---|---|
| 超越函数太贵 | 纯乘法 vs sigmoid | 1.5405 vs 1.5401 ms，**排除** |
| 跨步访问 | 改连续输入 | 245→457，只解释一半 |
| 硬件带宽不足 | torch 同形状三流运算 1331 GB/s | **排除** |
| program 太多 | 行宽 2048→14336（57344→8192 个） | 全部 1.54 ms，**排除** |
| 启动开销 | 规模 128→8192 线性缩放 | **排除** |
| mask 未消除 | 静态 shape + 静态 tile | 仍 457 GB/s，**排除** |

**最终判断**：问题在九齿对纯元素级路径的代码生成，非应用层可绕过。

### 10.2 C++ AOT 导出不可用

比赛要求算子经九齿编译链生成目标代码并进入正式推理路径。
我们尝试用九齿的 AOT 能力（`caller="cuda"`）导出 C++ 源码，
以便挂接到 `infiniop` 的 hygon 后端：

```
ninetoothed.make(..., caller="cuda", num_warps=2, num_stages=1)
→ subprocess.CalledProcessError: triton.tools.compile 返回非零
  signature '*bf16,*bf16,*bf16,i64,1,i64,...'
```

海光版 Triton 发行环境中，`triton.tools.compile` 这一独立 AOT 编译器无法运行。
**因此本阶段的算子停留在"独立可运行、可测量"的形态，尚未接入 C++ 推理主路径。**
